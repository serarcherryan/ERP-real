# Project Operating Model

## 1. 项目目标

养老院 ERP 系统需要支撑机构日常运营、护理服务、家属沟通、财务结算、库存资产、人事排班、风险告警和监管审计。系统的工程治理目标是让模块持续增多时仍然保持可维护、可测试、可扩展和可追责。

## 2. 端与用户角色

| 端 | 主要用户 | 核心目标 | 典型能力 |
| --- | --- | --- | --- |
| 管理端 | 院长、运营经理、财务、人事 | 全局运营和配置 | 机构配置、报表、审批、权限 |
| 员工端 | 护士、护工、医生、后勤 | 高频业务执行 | 护理任务、巡房、记录、告警处理 |
| 家属端 | 老人家属 | 信息透明和互动 | 账单、健康动态、探视预约、消息 |
| 企业端 | 连锁集团、合作机构 | 多机构管理 | 多租户、经营看板、统一标准 |
| 监管/审计端 | 内控、外部监管 | 数据追溯 | 审计日志、合规报表、风险记录 |

## 3. 需求分层

| 层级 | 定义 | 例子 | 产物 |
| --- | --- | --- | --- |
| L0 战略能力 | 系统必须长期具备的能力 | 多机构管理、护理闭环、财务闭环 | 路线图、能力地图 |
| L1 业务域 | 独立演进的业务边界 | 入住、护理、药品、库存、财务 | 领域模型、模块边界 |
| L2 业务流程 | 跨角色的端到端流程 | 入住办理、护理计划执行、退住结算 | 流程图、验收标准 |
| L3 功能点 | 可开发和验收的功能 | 创建护理任务、上传生命体征 | PRD、接口契约 |
| L4 工程任务 | 可提交代码的任务 | 表结构、API、页面、测试 | Issue、PR |

## 4. 工作流

1. 需求进入：所有需求必须说明用户角色、业务目标、验收标准和影响模块。
2. 模块设计：新增模块必须填写模块模板，明确数据、接口、权限、审计和告警。
3. 契约评审：跨端、跨服务、跨模块的 API 或事件必须先评审契约。
4. 实现开发：代码变更必须关联 Issue 或模块设计。
5. 质量门禁：测试、权限、性能、审计、回滚方案必须满足对应等级。
6. 发布复盘：重要发布必须记录指标、事故、回滚和后续事项。

## 5. RACI

| 活动 | Product | Tech Lead | Backend | Frontend | QA | SRE/Security |
| --- | --- | --- | --- | --- | --- | --- |
| 业务目标 | A | C | I | I | C | I |
| 模块边界 | C | A | R | C | C | C |
| API 契约 | C | A | R | R | C | C |
| 数据模型 | C | A | R | I | C | C |
| 测试策略 | C | A | R | R | A/R | C |
| 性能容量 | I | A | R | C | C | R |
| 安全合规 | C | A | R | R | C | A/R |
| 发布回滚 | I | A | R | R | R | R |

A = Accountable, R = Responsible, C = Consulted, I = Informed.

## 6. Done Definition

一个功能被认为完成，至少需要满足：

- 需求验收标准已覆盖
- API 契约或页面行为已记录
- 权限、审计、数据隐私已处理
- 单元测试、集成测试或 E2E 测试达到风险匹配程度
- 关键路径有日志、指标和错误处理
- 数据迁移、回滚和兼容策略明确
- PR 描述包含影响面和验证结果
