# Test Case Lifecycle

## 1. 目的

本文件定义测试用例从生成、实现、执行、检查、修复到回归的完整闭环。任何功能、缺陷修复、重构、接口、事件、权限、状态机或数据迁移变更，都必须按风险等级执行匹配的测试流程。

测试不是最后的补丁，而是需求和契约的一部分：

```text
需求/契约
-> 生成测试用例
-> 实现自动化测试或记录手工验收步骤
-> 执行测试
-> 检查失败
-> 修复代码或修正用例
-> 回归复跑
-> 记录结果和剩余风险
```

## 2. 适用范围

| 变更类型 | 是否需要测试用例 | 最低要求 |
| --- | --- | --- |
| 新业务功能 | 是 | 用例清单 + 自动化测试 + 关键路径验收 |
| Bug 修复 | 是 | 先补复现用例，再修复，再回归 |
| API 变更 | 是 | 契约测试 + 权限/租户测试 + 错误码测试 |
| 事件变更 | 是 | 事件 schema、幂等、重试、死信测试 |
| 状态机变更 | 是 | 合法流转 + 非法流转 + 并发冲突测试 |
| 权限/审计变更 | 是 | 越权、字段权限、审计落库测试 |
| 数据迁移 | 是 | 迁移前后校验 + 回滚演练 |
| 性能相关变更 | 是 | 压测用例 + 指标观察 |
| 纯文案/样式 | 可简化 | 说明跳过自动化原因，做基础验收 |
| 测试内部整理 | 可简化 | 保证原有测试通过 |

## 3. 测试用例生成规则

每个需求或代码变更应从以下来源生成测试用例：

| 来源 | 必须提取的测试点 |
| --- | --- |
| 业务验收标准 | 正常路径、边界条件、角色差异 |
| 模块设计文档 | 领域不变量、数据所有权、并发与一致性 |
| API 契约 | 请求参数、响应结构、错误码、限流、兼容性 |
| 事件契约 | Payload、幂等键、顺序要求、重试和死信 |
| 权限设计 | 功能权限、数据范围、字段权限、场景权限 |
| 安全合规 | 脱敏、敏感数据访问审计、导出审计 |
| 发布计划 | Feature flag、灰度、迁移、回滚 |

用例必须覆盖以下类别，风险不相关时可说明不适用：

- 正常路径
- 参数校验
- 空数据和边界值
- 权限不足
- 跨租户/跨机构越权
- 字段脱敏
- 幂等重复提交
- 并发冲突
- 非法状态流转
- 审计日志
- 异步重试和死信
- 降级或外部依赖失败

## 4. 测试用例文档位置

当需求较复杂、涉及 P0/P1 流程、跨模块、权限、审计、迁移或高并发时，必须创建测试用例文档：

```text
docs/05-quality/test-cases/<module>-<feature>-test-cases.md
```

示例：

```text
docs/05-quality/test-cases/resident-profile-create-test-cases.md
docs/05-quality/test-cases/work-order-transition-test-cases.md
docs/05-quality/test-cases/dashboard-metric-query-test-cases.md
```

小型变更可以不新增单独用例文档，但必须在 PR 或最终响应中列明：

- 覆盖的测试点
- 执行的测试命令
- 未覆盖原因和剩余风险

## 6. 执行顺序

测试执行应按从快到慢、从局部到全链路的顺序进行：

```text
静态检查 / 类型检查
-> Unit
-> Integration
-> Contract
-> Security / Permission
-> E2E
-> Performance
```

如果前置层级失败，默认先修复前置失败，再继续后续测试。只有在失败与本次变更无关、且已有负责人确认时，才允许记录为已知问题并继续。

## 7. 失败检查与修改规则

测试失败后必须先分类，再修改：

| 失败类型 | 处理规则 |
| --- | --- |
| 产品规则理解错误 | 回到需求、模块文档或契约确认，必要时更新文档 |
| 代码实现错误 | 修改实现，保留或增强失败用例 |
| 测试用例错误 | 修正用例，说明为什么原用例不符合契约 |
| 测试数据错误 | 修复 fixture，保证多租户、多机构、多角色覆盖 |
| 环境/依赖失败 | 记录环境问题，能本地替代则补 mock 或 Testcontainer |
| 已知历史失败 | 标记来源、负责人、影响范围，不得静默忽略 |

禁止为了通过测试而删除关键断言、扩大权限、移除租户过滤、关闭审计或放宽状态机规则。

## 8. 回归复跑规则

每次修复后必须复跑：

- 失败用例本身。
- 同模块相关单元测试。
- 涉及 API/事件时复跑契约测试。
- 涉及权限、租户、审计时复跑安全测试。
- 涉及状态机时复跑合法和非法流转测试。
- 涉及高并发路径时复跑并发或压测用例。

若复跑无法完成，最终说明必须包含：

- 未执行的测试项
- 未执行原因
- 风险影响
- 后续补测建议

## 9. 风险等级与最小测试集

| 风险等级 | 适用场景 | 最小测试集 |
| --- | --- | --- |
| P0 | 长者档案、医疗、药品、财务、权限、工单主流程、数据隔离 | Unit + Integration + Contract + Security + 关键 E2E |
| P1 | 重要业务流程、驾驶舱、活动、物资、通知 | Unit + Integration + Contract 或关键路径验收 |
| P2 | 普通配置、低风险查询、内部工具 | Unit 或基础验证 |
| Low | 文案、样式、注释 | 手工验收或说明无需测试 |

## 10. AI 执行要求

AI Agent 在实现代码前必须先回答三个问题：

- 本次变更应新增或更新哪些测试用例？
- 哪些用例必须自动化，哪些可以手工验收？
- 需要执行哪些命令或检查来证明变更有效？

AI Agent 在结束任务前必须报告：

- 生成或更新的测试用例。
- 新增或修改的测试文件。
- 实际执行的测试命令和结果。
- 失败项、修复动作和复跑结果。
- 未覆盖项和剩余风险。

## 11. 完成标准

测试闭环完成必须同时满足：

- 用例覆盖变更的核心业务规则和风险点。
- 自动化测试或手工验收步骤已执行。
- 失败项已修复并复跑，或明确记录为已知风险。
- 权限、租户隔离、审计、幂等、并发影响已检查。
- 最终输出包含测试结果和未覆盖说明。
