# ADR-0002: Frontend Stack

| 字段 | 内容 |
| --- | --- |
| 状态 | Accepted |
| 日期 | 2026-04-25 |
| 决策人 | TBD |
| 影响范围 | Web 管理端、小程序端、前端工程化、UI 组件体系 |

## Context

平台需要支持多套视图：物业管理、养老中心、运营驾驶舱、系统管理、员工小程序和用户/家属小程序。页面以 ERP 场景为主，包含大量表格、表单、流程状态、权限菜单、数据看板和移动端待办操作。

前端需要满足：

- Web 端适合后台业务高频操作。
- 小程序端适合员工现场处理和用户/家属轻量交互。
- 多端共享 TypeScript 类型、接口契约和部分业务校验。
- UI 风格偏工作台和运营系统，不做营销式页面。

## Decision

Web 管理端采用 React + TypeScript + Ant Design Pro。小程序端采用 Taro + React + TypeScript，优先支持微信小程序。

前端通过 OpenAPI 生成请求类型和 DTO，Web 与小程序共享基础类型、权限常量、字典和校验工具。

## Options Considered

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| React + Ant Design Pro + Taro | ERP 组件成熟，TypeScript 生态好，多端技术栈一致 | 需要控制 Ant Design 页面复杂度和小程序包体积 | 采纳 |
| Vue + Element Plus + uni-app | 国内生态成熟，团队上手快 | Web 和小程序组件体系差异仍需治理 | 备选 |
| 原生微信小程序 + 独立 Web | 端侧能力强 | 类型、契约和组件复用弱，维护成本高 | 不采纳 |
| Flutter 多端 | 体验一致 | ERP Web 表格表单生态和团队成本存在风险 | 不采纳 |

## Consequences

- 正面影响：Web 端能快速交付复杂后台，小程序端与 Web 保持同一语言和部分逻辑复用。
- 负面影响：需要建立严格的前端分层，避免页面直接堆业务规则。
- 成本：需要维护共享包、接口生成、权限路由、组件规范和设计令牌。
- 后续工作：定义前端目录、权限菜单模型、OpenAPI 代码生成和小程序包体积策略。

## Validation

- 如何证明这个决策有效：首期 Web 和小程序共用接口类型，完成档案、工单和驾驶舱关键流程。
- 需要观察的指标：页面首屏时间、接口错误率、构建时间、小程序包体积、关键流程完成率。
- 需要复盘的时间点：首期 MVP 上线后、小程序包体积接近平台限制时。
